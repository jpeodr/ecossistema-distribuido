Arquitetura de solução

Topologia distribuída adotada no ecossistema SIDRA/IBGE, diagramas UML dos componentes, da implantação, da sequência, das classes e da atividade, além do cálculo de speedup medido no sistema.

Resumo

  • Três tipos de nó: Manager (coordena), Workers (executam) e Redis (fila).
  • Um contêiner por nó, rede bridge única, orquestração por Docker Compose.
  • 27 tarefas por job, uma por Unidade da Federação, consumidas por qualquer Worker.
  • Três níveis de paralelismo: entre os nós, dentro do nó (I/O) e dentro da tarefa (CPU).
  • Speedup medido contra o teto teórico da lei de Amdahl, com os números do último job.

Visão geral #

O sistema é um ecossistema de processos distribuídos com topologia mestre-escravo com broker (produtor/consumidor). O Manager é o mestre: recebe o pedido, fatia o job e publica as tarefas. O Redis é o broker: guarda a fila. Os Workers são os escravos: retiram tarefas e devolvem resultados.

Nenhum Worker conhece os demais e nenhum Worker conversa com outro Worker. A única interação é com o Redis (retirar tarefas) e com o Manager (devolver resultados). Isso permite escalar horizontalmente com docker compose up -d --scale worker=N.

A API do SIDRA fica fora do ecossistema: é um serviço público do IBGE, acessado por HTTPS. O sistema não escreve no SIDRA, apenas lê.

Diagrama de implantação #

Topologia física: um host Docker com a rede bridge ecossistema, um contêiner do Manager (porta 8000 publicada), um do Redis e N de Worker. O Manager e os Workers compartilham a mesma imagem Docker; o que muda é o comando de entrada.

Diagrama de componentes #

Componentes internos e as interfaces entre eles: o painel web e o script de demonstração consomem a API do Manager; o Manager publica no Redis e grava no SQLite; o Worker puxa da fila, lê no SIDRA e devolve ao Manager.

Ciclo de vida de um job #

Sequência completa: do pedido HTTP ao relatório. Destacam-se a sondagem do período (para não despachar um job para um período sem dados) e o disparo do REDUCE na chegada da última tarefa.

Modelo de domínio #

Entidades que atravessam o sistema: Dataset (com suas variáveis e categorias), JobRequest, Task, Record e TaskResult, com a persistência em Store e a agregação em Reduce.

Fluxo de execução #

Atividade do Manager e do Worker, incluindo o caminho de erro: falha na consulta ao SIDRA gera re-enfileiramento com espera de 1 s e 2 s, até o limite de MAX_RETRIES.

Paralelismo #

O paralelismo aparece em três níveis, com granularidades diferentes. Os três somam: o job é quebrado em tarefas independentes (nível 1), cada tarefa é executada junto de outras no mesmo processo (nível 2) e o trabalho de CPU de cada tarefa sai da thread de event loop (nível 3).

Nível 1 · entre os nós

Distribuído

— tarefas

Uma tarefa por UF: 27 consultas independentes ao SIDRA, espalhadas pelos Workers que retiram tarefas da fila.

Nível 2 · dentro do nó

Assíncrono (I/O)

— tarefas em voo

Cada Worker mantém até WORKER_CONCURRENCY requisições simultâneas ao SIDRA (asyncio.create_task).

Nível 3 · dentro da tarefa

Thread (CPU)

1 thread dedicada

A normalização com pandas roda em asyncio.to_thread para não bloquear o event loop.

Como as tarefas se distribuem

O Manager publica as 27 tarefas com um único RPUSH em pipeline. A fila é compartilhada: qualquer Worker pode retirar qualquer tarefa, e a ordem de atendimento é livre. Não há afinidade entre tarefa e Worker, nem estado compartilhado entre Workers.

Com 3 Workers e WORKER_CONCURRENCY=4, o ecossistema mantém 12 requisições simultâneas ao SIDRA — 12 tarefas em voo ao mesmo tempo, cada uma em um processo diferente.

O gargalo real é externo: a latência da API do SIDRA. Por isso o paralelismo do nível 2 é de I/O (não de CPU) e o nível 3 existe só para tirar a normalização com pandas da thread de event loop.

Speedup #

O speedup mede quanto mais rápido o job roda quando o trabalho é distribuído, em relação à execução serial equivalente.

Speedup S = T₁ / Tₚ T₁ = tempo serial de referência Tₚ = tempo observado com os Workers em paralelo

A lei de Amdahl define o teto: uma fração sequencial do programa (1 − P) não pode ser paralelizada e limita o ganho total.

Speedup máximo S_max(N) = 1 / ((1 − P) + P / N) P = fração paralelizável do programa (0 a 1) 1 − P = fração sequencial, que não pode ser paralelizada N = número de processadores ou núcleos disponíveis

Exemplo genérico: com 80% do programa paralelizável (P = 0,8) e 4 processadores (N = 4), S_max = 1 / (0,2 + 0,2) = 2,5. Com 16 processadores o mesmo programa chega a no máximo 1 / (0,2 + 0,05) ≈ 4 — mais núcleos não resolvem a fração sequencial.

Aplicação no sistema

No ecossistema, a fração paralelizável é praticamente o job inteiro: as 27 tarefas são independentes. O que sobra de sequencial é o REDUCE, executado uma única vez no Manager quando a última tarefa chega.

T₁ = Σ duração das 27 tarefas + t_REDUCE Tₚ = finished_at − started_at do job P = (Σ duração das tarefas) / T₁ N = Workers × WORKER_CONCURRENCY (3 × 4 = 12) S = T₁ / Tₚ S_max = 1 / ((1 − P) + P / N)

Comparando o speedup observado com o teto de Amdahl, a diferença é o custo da distribuição: tempo de espera na fila, ida e volta do callback, latência de rede até o SIDRA e o ramp-up do pool de tarefas no início do job.

Leitura do resultado

  • O teto teórico é calculado com N slots, não com a contagem de máquinas: quem executa em paralelo são as requisições ao SIDRA, não os contêineres.
  • Com P ≈ 1, o teto é praticamente N: o speedup acompanha a escala linear enquanto a fração sequencial for pequena.
  • Se a fração sequencial crescer (por exemplo, um REDUCE mais pesado), o teto cai mesmo com mais Workers — é o caso que a lei de Amdahl descreve.
